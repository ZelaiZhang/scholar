# Research OS 日常驾驶舱优化设计

日期：2026-08-12  
状态：依据用户“继续优化、真正好用且不再反复询问”的授权进入实施

## 1. 目标

当前版本已经具备课题模板、来源登记、PDF 提取、证据校验、模型适配和十个 Codex 技能，但日常使用仍要求用户记忆命令、目录和阶段顺序。本轮优化把它从“工具箱”变成“每天打开就知道下一步做什么”的科研驾驶舱。

成功标准是：研零用户无需理解内部目录协议，只运行一个命令，就能看到环境是否正常、课题进度、当前阻塞和一条可直接交给 Codex 的下一步指令。

## 2. 范围

本轮新增四项能力：

1. `research-os doctor`：检查安装、工作区结构、中文终端、技能目录、来源登记表和项目可读性，并给出可执行修复建议。
2. `research-os guide [--project SLUG]`：显示课题驾驶舱，识别未开始、进行中、已产出和受阻阶段，只推荐一个下一步。
3. `research-os add-sources MANIFEST --project SLUG`：从 UTF-8 文本清单批量登记 DOI、arXiv、URL 和本地文件并关联课题；先校验全部输入，再原子写入，拒绝半成功。现有 `add-source` 同样增加可选 `--project`。
4. 新课题元数据与快速入口：生成 `project.yaml` 和 `START-HERE.md`，同时兼容第一版已经存在但没有元数据的课题。

不增加 Web 服务、数据库、向量检索、实验执行、自动联网检索或真实医疗数据处理。

## 3. 用户路径

### 3.1 首次使用

```powershell
research-os doctor
research-os new-project --title "医疗诊断大模型可靠推理" --slug medical-reasoning
research-os guide --project medical-reasoning
```

`doctor` 只做只读检查。`new-project` 生成课题材料和快速入口。`guide` 输出当前状态以及一条可以直接复制到 Codex 的 `$research-project-init` 指令。

### 3.2 日常使用

用户每天只需运行：

```powershell
research-os guide --project medical-reasoning
```

系统按证据优先顺序判断下一步：研究简报、来源导入、论文精读、文献综合、Idea 审查、实验设计、结果解读、写作、模拟审稿。它不自动推进阶段，也不把文件存在等同于内容完成。

### 3.3 批量导入

清单每行一个来源，允许空行和以 `#` 开头的注释：

```text
doi:10.1000/example
arXiv:2401.01234
https://example.org/paper
./inbox/paper.pdf
```

相对文件路径以清单所在目录为基准解析。任何一行无效时，命令列出行号和原因，不写入登记表。全部通过后一次性写入，并汇总新增、重复和已升级外发许可的数量；指定 `--project` 时把结果中的 `source_id` 幂等写入该课题的 `project.yaml`。

## 4. 组件设计

### 4.1 工作区诊断 `doctor.py`

诊断结果使用 `pass`、`warn`、`fail` 三种等级，每项包含名称、简短说明和修复动作。检查项包括：

- Python 版本满足 `>=3.11`；
- 当前目录包含 Research OS 标志文件；
- `.agents/skills` 中十个科研技能可读；
- `projects/`、`library/` 和 `inbox/` 存在；
- 来源登记表可解析，且已登记本地文件哈希未漂移；
- 标准输出是否为 UTF-8；非 UTF-8 时提示 Windows 修复命令；
- 每个课题的必需文件是否齐全。

存在 `fail` 时退出码为 `1`，只有 `warn` 时仍返回 `0`，方便用户区分不可用与建议优化。

### 4.2 课题状态 `guidance.py`

状态分析保持确定性，不调用模型。新课题的 `project.yaml` 保存 schema 版本、标题、slug、创建时间和该课题关联的 `source_ids`。对于旧课题，从目录名和研究简报一级标题回退推断，但绝不把全局来源擅自归给旧课题。

阶段状态通过下列信号组合判断：

- 文件与打包模板完全一致：`未开始`；
- 文件已被修改但阶段质量门禁尚未通过：`进行中`；
- 存在相应产物且确定性校验通过：`已产出`；
- 所需文件缺失、来源损坏或证据校验失败：`受阻`。

`guide` 只给出一个下一步，避免输出长清单制造新的决策负担。推荐内容包含原因、目标文件和可复制的 Codex 技能指令。

### 4.3 批量来源登记

`sources.py` 增加无副作用的预检与批量事务接口：先规范化全部来源、计算本地文件哈希、检测清单内部重复和现有记录，再通过现有原子写入函数一次提交。

批量导入沿用第一版规则：

- 内容相同的本地文件复用同一 `source_id`；
- 不覆盖首次人工笔记；
- 只有显式参数才升级外部 API 许可；
- 单条和批量登记都可通过 `--project` 建立课题关联，重复执行不会重复写入 ID；
- 错误信息包含清单行号，但不泄露 API Key；
- 清单文件自身不会被当作科研来源登记。

### 4.4 新课题入口

`project.yaml` 是机器可读元数据，只保存身份信息和明确关联的 `source_ids`，不保存模型判断。`START-HERE.md` 只包含三件事：先运行什么命令、当前课题关键文件在哪里、严禁导入哪些医疗数据。核心模板仍保持可独立编辑，不引入隐藏状态。

## 5. 错误与兼容策略

- 所有现有 CLI 命令和参数保持兼容。
- 旧课题缺少 `project.yaml` 时由 `guide` 自动回退读取标题，不强制迁移；来源归属显示“未关联”，不使用全局数量猜测。
- `guide` 发现未知模板版本时保守显示“需要人工检查”，不猜测完成状态。
- `doctor` 不修改工作区；修复动作必须由用户或 Codex 显式执行。
- 批量导入采用全有或全无语义；输入错误时登记表字节内容保持不变。
- 中文输出继续使用 UTF-8 源文件；README 和 `doctor` 给出 Windows 一次性入口，测试覆盖 UTF-8 输出文案。

## 6. 测试策略

严格采用测试驱动开发：

1. 先测试 `doctor` 对健康工作区、缺失目录、损坏登记表和非 UTF-8 控制台的判定。
2. 先测试 `guide` 对新课题、旧课题、模板已编辑、证据失败和产物推进的下一步推荐。
3. 先测试批量清单的注释、相对路径、重复项、行号错误、原子回滚和课题来源关联。
4. 先测试新建课题新增元数据与快速入口，同时验证安装后模板仍可用。
5. 最后执行全量测试、wheel 安装冒烟测试、技能校验和真实 CLI 路径走查。

## 7. 验收标准

- 首次用户运行 `doctor` 后能明确知道是否可用以及如何修复问题。
- 没有课题时，`guide` 给出创建课题的唯一下一步。
- 新课题和旧课题都能得到稳定、确定性的阶段状态与下一步指令。
- 多课题工作区只统计各自显式关联的来源，不发生跨课题误判。
- 用户无需记住十个技能的先后顺序。
- 批量清单包含一个坏来源时不产生任何部分写入。
- 所有旧测试继续通过，新增行为均有先失败后通过的自动测试。
- 不运行实验、不上传未授权内容、不覆盖人工文件、不削弱证据门禁。
