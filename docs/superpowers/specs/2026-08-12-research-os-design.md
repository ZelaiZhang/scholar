# Research OS 设计规格

日期：2026-08-12  
状态：已完成方案讨论，等待书面规格确认

## 1. 背景与目标

Research OS 是面向大模型方向研究生的 Codex 原生科研导航工作区。它覆盖从模糊方向形成研究问题，到文献管理、创新点审查、实验设计指导、结果解读、论文写作和返修的完整流程。

系统的目标不是代替研究者作判断，而是减少重复整理工作，保留论证依据，让每个重要结论都可追溯、可复核、可继续修改。

首个应用方向是医疗诊断大模型与推理研究，同时兼容大模型文本处理、微调、量化和强化学习等课题。系统只提供这些实验的设计与分析指导，不负责训练、量化、强化学习或集群任务执行。

## 2. 用户与使用边界

### 2.1 目标用户

- 主要用户是一名处于研零阶段的大模型方向研究生。
- 用户使用 Codex 工作区完成日常科研导航。
- 用户可能拥有多卡服务器，但训练基础设施不属于本系统。
- 用户可以选择接入 DeepSeek 等 OpenAI-compatible API。

### 2.2 数据边界

- 第一版只处理公开论文、公开网页、公开数据集说明、研究笔记和脱敏示例。
- 第一版禁止导入真实病例、可识别病历或其他个人健康信息。
- 外部模型调用默认关闭，由用户显式配置后启用。
- 原始输入与模型生成内容必须分开保存，生成内容不得覆盖原文。

### 2.3 非目标

- 不执行模型训练、微调、量化、强化学习或集群调度。
- 不替代 Zotero、LaTeX、训练框架或正式统计软件。
- 不提供临床诊断、治疗建议或医疗决策。
- 不自动宣称研究创新成立；候选创新点必须经过证据审查和人工确认。
- 第一版不建设 Web 界面、数据库服务或向量数据库。

## 3. 设计原则

1. **证据优先**：事实性陈述必须关联来源及其定位信息。
2. **人类可读**：核心成果使用 Markdown、YAML、JSON 或 CSV 保存。
3. **本地优先**：资料和科研记录默认留在本地工作区。
4. **模型可替换**：外部模型通过统一接口调用，不绑定单一厂商。
5. **渐进增强**：未配置外部 API 时，核心流程仍可由 Codex完成。
6. **人工把关**：选题、创新点、关键引用和论文定稿均设人工确认门禁。
7. **可复现**：记录输入、提示词版本、模型、参数、时间和产物路径。
8. **轻量维护**：第一版不引入必须长期运行的服务。

## 4. 总体架构

系统分为五个边界清晰的部分：

1. **工作区协议**：目录结构、命名规范、状态文件和 `AGENTS.md` 行为约束。
2. **科研技能**：由 Codex 调用的阶段化工作流，每个技能只承担一种科研任务。
3. **文档与证据层**：原始资料索引、论文卡片、文献矩阵、证据账本和写作成果。
4. **确定性工具层**：负责 PDF 文本提取、元数据获取、格式校验和外部模型请求。
5. **质量门禁层**：检查来源、引用、推断标记、完整性、隐私边界和产物结构。

数据流如下：

```text
PDF / DOI / arXiv / URL / 笔记
              |
              v
       inbox 清单与原始索引
              |
              v
       论文分诊与结构化卡片
              |
              v
  文献矩阵 <-> 证据账本 <-> 冲突记录
              |
              v
   研究问题 -> Idea 审查 -> 实验设计指导
              |
              v
       结果解读 -> 写作 -> 模拟审稿/返修
```

## 6. 核心数据对象

### 6.1 Source Record

表示一个原始来源，包含：

- 稳定的 `source_id`；
- 来源类型：PDF、DOI、arXiv、URL 或笔记；
- 标题、作者、年份、标识符与原始位置；
- 导入时间、内容哈希和解析状态；
- 是否允许发送给外部 API；
- 元数据核验状态。

### 6.2 Paper Card

每篇论文对应一张结构化卡片，至少包含：

- 研究问题与动机；
- 方法、模型、数据集、基线与指标；
- 主要结论及对应页码、章节或原文定位；
- 局限、威胁与复现条件；
- 与当前课题的相关性；
- 研究者自己的批注；
- 模型生成部分的 provenance 信息。

卡片中的内容必须区分 `reported_fact`、`model_inference` 和 `researcher_note`。

### 6.3 Evidence Item

证据账本中的每一项包含：

- `claim_id` 和规范化陈述；
- 类型：事实、推断或假设；
- 支持来源、反对来源及原文定位；
- 证据强度与置信说明；
- 当前状态：未核验、部分核验、已核验或存在冲突；
- 可用于论文的范围和限制。

### 6.4 Research Project

每个课题是一个独立目录，固定包含：

```text
00-research-brief.md
01-search-log.md
02-evidence-ledger.yaml
03-literature-review.md
04-idea-candidates.md
05-experiment-design.md
06-result-analysis.md
writing/
reviews/
artifacts/
```

课题状态通过小型 YAML 文件记录，状态只允许在质量门禁通过后向下一阶段移动。

## 7. 阶段化科研工作流

### 7.1 课题定义

输入模糊方向，输出研究对象、任务边界、核心问题、关键词组、可验证目标、资源约束和停止条件。医疗方向必须额外记录临床相关性、数据来源风险和可能的误用方式。

### 7.2 资料导入与分诊

- 本地 PDF 是第一优先入口。
- 同时接受 DOI、arXiv、URL 和 Markdown 笔记。
- 导入后先创建来源记录，再进行内容解析。
- 分诊输出相关性、证据类型、阅读优先级和排除原因。
- 对无法读取全文的来源只处理可获取的内容，并明确标注范围。

### 7.3 结构化精读

从原文生成论文卡片，不允许只依据标题或摘要推断全文方法与结论。关键信息必须尽量附带页码或章节。无法确定时使用明确的“不确定”标志，禁止补全不存在的信息。

### 7.4 文献综合

对多篇论文生成：

- 方法与实验设置对比矩阵；
- 已形成的共识；
- 相互冲突的结论及可能原因；
- 尚未覆盖的问题；
- 可能由数据泄漏、指标选择或不可比设置造成的伪优势；
- 下一轮检索建议。

### 7.5 Idea 工作台

候选创新点必须通过以下检查：

- 是否只是更换模型、数据集或提示词；
- 最近工作是否已经完成相同贡献；
- 是否存在可靠基线和可获得数据；
- 是否能设计关键消融与失败判据；
- 是否有清楚的科学问题，而不仅是工程组合；
- 医疗场景是否存在高风险外推或不恰当诊断表述。

系统输出候选项、反对意见、所需证据和建议优先级，由用户决定是否立项。

### 7.6 实验设计指导

系统只生成设计材料，包括：

- 假设和操作化定义；
- 数据划分与泄漏检查；
- 基线、消融和对照；
- 主指标、辅助指标、统计检验与置信区间；
- 算力预算估算方法；
- 预期失败模式和停止条件；
- 可复现性清单。

任何训练命令、集群配置或实验执行均属于课题自身代码库，不由 Research OS 执行。

### 7.7 结果解读

用户可导入表格、图形说明或日志摘要。系统检查：

- 与预注册假设是否一致；
- 是否存在只报告最佳结果的倾向；
- 指标改善是否具有统计和实际意义；
- 是否需要补充对照或消融；
- 结论是否超出数据支持范围；
- 医疗研究中是否混淆技术指标与临床效用。

### 7.8 写作、模拟审稿与返修

写作只能从已经核验的证据账本取事实性材料。系统支持论文大纲、段落草稿、图表说明、摘要压缩、语言润色和引用缺口检查。

模拟审稿至少包含四种视角：方法、统计、医疗安全和严格综合审稿。返修阶段建立“审稿意见—作者回应—修改位置—新增证据”的对应矩阵。

## 8. Codex 技能设计

第一版提供以下小而独立的技能：

1. `research-project-init`：从研究方向创建规范课题目录。
2. `paper-intake`：登记来源并执行分诊。
3. `paper-deep-read`：生成可追溯论文卡片。
4. `literature-synthesis`：维护矩阵、证据与冲突。
5. `idea-review`：生成候选创新点并进行反向审查。
6. `experiment-advisor`：生成实验设计建议，不运行实验。
7. `result-interpreter`：检查结果与结论的对应关系。
8. `manuscript-assistant`：基于核验证据辅助写作。
9. `mock-reviewer`：多视角审稿与返修矩阵。
10. `research-weekly-review`：汇总进展、阻塞和下周行动。

每个技能必须明确输入、输出路径、允许修改的文件、质量检查和停止条件，不使用隐藏的长期状态。

## 9. 外部模型适配

### 9.1 Provider 接口

外部模型使用统一请求对象：

- provider 与 model；
- system/user 内容；
- temperature、最大输出长度和超时；
- 结构化输出 schema；
- 数据是否允许外发。

响应保存正文、模型标识、调用时间、参数、用量信息和错误状态。

### 9.2 模型角色

- `quality`：研究设计、复杂综合和关键写作。
- `economy`：批量格式化、初筛和低风险摘要，可指向 DeepSeek。
- `reviewer`：使用不同模型对重要成果进行独立审查。

角色只是一层配置映射。用户可选择 DeepSeek 或其他 OpenAI-compatible 服务，也可以完全不配置外部模型。

### 9.3 凭据与隐私

- Key 只从环境变量读取。
- `.env`、本地原始 PDF、缓存和请求日志正文默认进入 `.gitignore`。
- 请求前检查来源记录的外发许可。
- 日志不得包含 API Key。
- 外部 API 失败时保留本地产物，不创建伪成功结果。

## 10. 错误处理

- **PDF 无文本层**：标记为需要 OCR，不凭空生成卡片。
- **链接不可访问**：保存元数据和失败原因，允许稍后重试。
- **元数据冲突**：保留候选值并要求人工确认。
- **页码定位失败**：将证据标记为未核验，禁止进入正式写作材料。
- **结构化输出不合法**：保留原响应，执行有限次数的修复解析；仍失败则退出并报告。
- **外部 API 缺失或超时**：回退到 Codex 手工工作流或给出可执行提示，不中断已有资料。
- **重复导入**：根据标识符和内容哈希识别，不覆盖人工笔记。
- **隐私边界违规**：停止处理并指出不允许进入系统的材料。

## 11. 质量与测试策略

### 11.1 单元测试

- 配置加载与环境变量解析；
- 来源 ID 和内容哈希生成；
- DOI、arXiv 和 URL 规范化；
- YAML/JSON schema 校验；
- provider 响应和错误映射；
- 隐私与外发许可检查。

### 11.2 集成测试

- 本地 PDF 到来源记录和论文卡片；
- URL/DOI 到已核验元数据；
- 多篇卡片到文献矩阵与证据账本；
- 外部模型成功、超时、无 Key 和非法结构化输出；
- 重复执行不覆盖人工内容。

测试使用体积小、许可清晰的公开样例和伪造元数据，不把真实病例放入测试夹具。

### 11.3 内容质量检查

- 每个事实性 claim 至少有一个来源定位；
- 引用元数据无凭空补全字段；
- 推断与假设具有显式标签；
- 文献综合同时报告支持和冲突证据；
- 论文写作不引用未核验条目；
- 医疗文本不出现未经证据支持的临床效用宣称。

## 12. 第一版交付范围

第一版交付以下可工作的垂直切片：

1. 工作区规则、配置样例和中文使用说明。
2. 新建课题与固定目录模板。
3. 本地 PDF、DOI、arXiv、URL 和笔记的来源登记。
4. 文本型 PDF 的解析和结构化论文卡片生成流程。
5. 文献矩阵、证据账本和研究空白工作流。
6. Idea 审查、实验设计指导、结果解读、写作和模拟审稿模板。
7. Codex 阶段化科研技能。
8. DeepSeek/OpenAI-compatible 可选 provider。
9. schema、隐私边界和关键工具的自动测试。

OCR、Zotero/Obsidian 同步、图数据库、向量检索、Web UI 和定时文献监控留作后续版本。

## 13. 验收标准

第一版在以下条件全部成立时视为完成：

- 用户可以用一条明确的 Codex 指令创建新课题。
- 用户可以导入本地 PDF 或公开链接，并得到来源记录。
- 文本型 PDF 能生成带原文定位和不确定性标记的论文卡片。
- 至少五张论文卡片可合成为文献矩阵、冲突列表和研究空白候选。
- 系统可从证据账本生成 Idea 审查、实验设计建议和论文大纲。
- 模拟审稿结果能追溯到稿件位置和证据条目。
- 未配置 DeepSeek Key 时，本地流程仍可用且错误信息明确。
- 配置 DeepSeek 后，可通过统一 provider 执行一次结构化输出请求。
- 重复导入和重复生成不会覆盖原始资料或人工笔记。
- 自动测试覆盖核心数据模型、provider、校验和关键失败路径。
- README 明确说明公开资料边界、API Key 设置方法和典型工作流。

## 14. 实施顺序

1. 建立工作区协议、数据 schema 和模板。
2. 以测试驱动方式实现配置、来源登记和校验。
3. 实现文本型 PDF 与公开链接导入。
4. 实现 OpenAI-compatible provider 和 DeepSeek 配置样例。
5. 编写并验证阶段化 Codex 技能。
6. 完成从课题创建到模拟审稿的端到端样例。
7. 运行自动测试和人工内容质量检查，补齐 README。

这一顺序先保证资料和证据的可靠结构，再引入模型生成能力，最后串联完整科研流程。
